# Simulation platform

The MVP uses a Go Simulation Manager and an on-demand KVM-capable OVH Public
Cloud instance. Microsandbox provides one microVM per run. Production ELT is
never dispatched to this path.

## Lifecycle

```text
PGMQ simulation job
  -> acquire READY host or create hourly OVH instance
  -> BOOTING: wait for the configured private address
  -> BOOTSTRAPPING: verify cloud-init, KVM, and msb doctor
  -> create restricted Microsandbox microVM from immutable runtime digest
  -> prepare deterministic Postgres source and destination
  -> run the same Python ELT implementation
  -> evaluate destination and stream safe protobuf evidence
  -> destroy microVM and its exact run directory
  -> mark host IDLE
  -> delete OVH instance after SIMULATION_HOST_IDLE_TIMEOUT
```

Host state is durable in `simulation_hosts`; runs reference the host with a
nullable foreign key. `MAX_SIMULATION_CONCURRENCY=1` is enforced for the MVP.
Region, flavor, private/public IPs, total capacity, runtime version, heartbeat,
and bounded error details are persisted. Run TTL and host start/idle/reconcile
intervals are configuration, not user input.

## Security boundary

- OVH creation explicitly attaches the configured private network.
- The manager requires a private address and strict SSH known-host checking.
- Microsandbox uses restricted security, default-deny networking, bounded CPU,
  RAM, root disk, and a server-selected profile.
- Per-run TLS material and a signed short-lived token are generated by Go and
  removed with the run directory.
- Runtime images must be immutable digests in production.
- Production connector credentials are not copied to a simulation microVM.
- Evidence metadata is sanitized; large artifacts use private Tigris/S3 URLs.

The OVH base image must present an SSH host certificate issued by the control
plane's trusted host CA. The cloud-init bootstrap pins Microsandbox 0.6.8 and
verifies the installer checksum before execution.

The literal Go VPS also needs a reviewed private route to the Public Cloud
simulation subnet; this is not created automatically by the current cloud-init.
Follow the cross-network and host-CA checks in
[`../../../arcyria-infra/docs/setup-guide.md`](../../infrastructure/setup/ovh-dokploy-microsandbox.md)
before enabling the worker.

## Rollout

Apply additive migrations independently, publish and sign the runtime image,
deploy exactly one simulation-manager replica, keep rollout mode `disabled`,
then enable one canary organization. The protected canary proves completion,
cancellation, evidence, artifact checksum, cleanup, and two queued runs before
general rollout. Self-hosted Dokploy manages the persistent manager container only;
the manager controls dynamic OVHcloud hosts directly.
