# MANTrixFlow — Strict ELT Pipeline Guide

A single, step-by-step guide to how the MANTrixFlow ELT pipeline works end to
end, from the UI click to rows landing in existing destination tables.

This guide replaces the previous scattered notes (`COMPLETE_ELT_AUDIT…`,
`STRICT_ELT_IMPLEMENTATION…`, `STRICT_ELT_SUMMARY…`,
`FRONTEND_IMPLEMENTATION_CHECKLIST…`, `SESSION_SUMMARY…`). All cross-cutting
rules now live in the Cursor rules at
[`.cursor/rules/strict-elt-invariants.mdc`](../../../.cursor/rules/strict-elt-invariants.mdc)
and [`.cursor/rules/elt-flow-diagram.mdc`](../../../.cursor/rules/elt-flow-diagram.mdc).

---

## 1. What the product does (in one paragraph)

MANTrixFlow extracts data from a source (SQL database or SaaS), **stages it in
an ephemeral DuckDB file**, runs user-authored **dbt-duckdb** SQL models, and
**delivers only the final model outputs** into already-existing destination
tables (e.g. `analytics.hd`). No raw tables, no `_dlt_*` tables, and no new
tables ever appear in the client's database.

---

## 2. The `schema.table` contract

`schema.table` is the **only** way users, the Go API, and the Python ELT
identify a source or destination object.

| Layer | Format | Example | Who enforces it |
| --- | --- | --- | --- |
| UI (Source Panel) | `schema.table` single input | `public.users` | `apps/arcyria-platform/lib/pipelines/schema-table.ts` — `parseQualifiedTable` |
| UI (Destination Panel) | `schema.table` single input for the final delivery table | `analytics.dim_users_hd` | Same helper + `useDiscoverDestinationTable` |
| Go RunConfig | `SourceStreamConfig.stream_key = "schema.table"` + `duckdb_table_name = "schema__table"` | see `apps/server/arcyria-server/internal/server/pipeline_bundle.go` — `buildSourceStreamConfigs` | Unit test `TestBuildSourceStreamConfigs_StrictShape` |
| DuckDB staging | `schema__table` (double underscore) | `raw.public__users` | `duckdbTableName()` in Go; `duckdbTableNameForStream()` in TS |
| dbt source ref | `{{ source('raw', 'schema__table') }}` | `{{ source('raw', 'public__users') }}` | Generated by `runner/dbt_handler.py` |
| dbt dest contract | `DbtSqlModel.dest_table = "schema.table"` | `analytics.dim_users_hd` | Validated by `_parse_dbt_sql_models` in Python |

There are **no separate `schema` and `table` fields anywhere in the saved
graph, the dispatched payload, or the ELT request body.**

## 3. End-to-end flow (5 phases)

```
UI  →  Go API  →  pgmq  →  Worker  →  Python ELT (Phases 0-5)  →  Callback  →  UI
```

### Phase 0 — Pre-flight checks (`runner/handlers/preflight_handler.py`)

1. `disk_guard.ensure_disk_budget(config)` — `available_gb ≥ plan_limit × 2`.
2. Incremental cursor column exists on the source (when `INCREMENTAL`).
3. Destination table exists (`information_schema.tables`). Hard-fails with a
   named error if missing.
4. Destination columns are a superset of the SQL model's output columns.
   Mismatch fails with `"column X not present in analytics.hd"`.
5. Primary keys are collected. If none, `write_disposition = append` and a
   `no_pk_warnings` entry is queued for the callback.

### Phase 1 — Extract + Stage (`runner/paths/duckdb_staged.py`)

- dlt extracts each `SourceStreamConfig` into DuckDB.
- Resource name is explicitly set to `schema__table`, so tables in different
  schemas never collide.
- Incremental cursor is restored from `last_state` in the RunConfig.
- Staging disk usage is tracked against `plan_limit` throughout.

### Phase 2 — dbt Transform (`runner/dbt_handler.py`)

- `dbt_config.mode = "ui_sql"` — dbt project is generated on the fly from
  `dbt_config.sql_models`.
- `sources.yml` maps `raw.schema__table` to every extracted stream.
- `dlt.dbt.package()` runs the dbt project against the same DuckDB file.
- Outputs live in `analytics.<output_table>` inside DuckDB.

### Phase 3 — Deliver (`runner/delivery_handler.py`)

- For each SQL model:
  - Re-check destination table existence + columns.
  - `write_disposition = merge` when a PK exists; otherwise `append` (with
    the queued warning from Phase 0).
  - dlt writes from DuckDB into the existing destination table. **Never
    `CREATE TABLE`.**

### Phase 4 — Cleanup (always in a `finally`)

1. `state_handler.extract(pipeline)` snapshots the cursor state.
2. DuckDB file is `os.remove()`d.
3. Temp dbt project directory is deleted.

### Phase 5 — Callback to the Go API

Payload always includes:

- `delivery_outputs: ["analytics.hd", …]`
- `delivered_tables: int`
- `delivery_failures: string[] | null`
- `staging_size_bytes: int`
- `dbt_models_run: int`
- `no_pk_warnings: string[] | null`
- `last_state: {...}` (durable cursor envelope)

The Go callback handler (`apps/server/arcyria-server/internal/server/callback.go`)
persists each of these fields into `pipeline_runs.run_metadata`.

## 4. Build a pipeline in the UI (step by step)

1. **Create a source connection** — `Workspace ▸ Connections ▸ New source`.
2. **Create a destination connection** — same place, pick the destination DB.
3. **Create a pipeline** — `Workspace ▸ Data pipelines ▸ New`.
4. **Source Panel** — in the *Tables* tab, add each table as
   `schema.table`. The Destination Panel will later reference these exact
   stream keys.
5. **Destination Panel** — per source table, fill in:
   - **Final delivery table** — `schema.table` (must exist).
   - The UI fires `POST /connections/destinations/:id/discover-table` on
     blur and renders column pills + primary-key hints.
   - If the destination has no PK, an amber hint warns that rows will be
     appended instead of merged.
6. **SQL model editor** — write the dbt staging `SELECT` using
   `{{ source('raw', 'schema__table') }}`. Click **Validate SQL** — the
   backend compares output columns against the destination columns and
   flags mismatches inline.
7. **Save** and click **Run**.

## 5. What the Run Status drawer shows

Three phase rows driven by the callback metadata:

- **Extract + Stage** — rows read, staging size.
- **dbt Transform** — models run / total.
- **Deliver** — delivered table names as chips (e.g. `analytics.hd`).

Warnings + errors:

- Amber banner for each `no_pk_warnings` entry.
- Red banner for each `delivery_failures` entry (named table + reason).
- If the run is `waiting`, the drawer says
  *"Waiting for ELT staging disk space. Auto-retrying every 30 s."*

## 6. The 12 invariants (authoritative source: Cursor rule)

The full text lives in
[`.cursor/rules/strict-elt-invariants.mdc`](../../../.cursor/rules/strict-elt-invariants.mdc).
Short form:

1. DuckDB file is always deleted in a `finally`.
2. Cursor state is extracted before the DuckDB file is deleted.
3. Destination table is never created — Phase 0 fails hard if it is missing.
4. Column mismatch fails with the offending column name.
5. No `_dlt_*` tables ever land in the client destination.
6. Credentials never appear in API responses, logs, or error messages.
7. Cross-tenant RLS is verified with real Supabase JWT tests.
8. Source tables are `schema.table`; DuckDB staging is `schema__table`.
9. Delivery is `merge` (with PK) or `append` + `no_pk_warnings` (no PK).
10. Disk check runs both in the Go dispatcher and in ELT Phase 0.
11. Callback payload carries `delivery_outputs`, `staging_size_bytes`,
    `dbt_models_run`, and `no_pk_warnings`.
12. No legacy ETL paths: no `cdc_direct.py`, `cleanup.py`,
    `TransformDrawer*`, `TransformNode*`, `TransformMiniCard*`,
    `transform_script`, or `LOG_BASED`.

## 7. Manual verification (before any ELT PR)

Run through these scenarios against a live stack:

1. **TC-1 Discover a destination table** — expect column pills + PK hints.
2. **TC-2 Validate a SQL model with an extra column** — expect an inline
   error naming the column missing from the destination.
3. **TC-3 Run with a missing destination table** — expect a `failed` run
   whose error message names the destination `schema.table`.
4. **TC-4 Run with a column drift on the destination** — expect a `failed`
   run whose error message names the offending column, `rows_written = 0`.
5. **TC-5 Run with a destination that has no PK** — expect a `success` run
   whose callback carries a `no_pk_warnings` entry; the Run Status drawer
   renders the amber banner.

The deep manual testing matrix (connector-by-connector) lives in
[`testing-local.md`](../../testing/local-development.md).
